# План и сверка с критериями

Артефакт работы с ИИ: план изменений, решения и воспроизводимые проверки. Конкретные результаты команд фиксируются в verification.md; ограничения не подменяются заявлениями о подтверждённой capacity.

## План выполненных изменений

1. Уточнить единицы: 100 млн голосов за минуту = 1,67 млн RPS; для capacity budget — 1,8 млн RPS. Удалить прежнюю трактовку 100 млн в секунду из основного профиля.
2. Сохранить горизонтальный API, durable Kafka enqueue и независимый worker. Не добавлять микросервисы ради структуры.
3. Добавить порт VoteAdmission и шардированную bounded map: атомарный резерв, 409 после ACK, 425 при конкурентной публикации, release при ошибке, 429 при заполнении без вытеснения активных ключей.
4. Настроить cookie affinity на ingress. Сохранить независимую SQL-дедупликацию worker для рестарта/редеплоя и replay.
5. Убрать SQL polling страницы голосования. Отделить подтверждение приёма от завершения подсчёта.
6. Перейти к агрегатам и минимальному durable ledger, без новых индивидуальных ответов. До первого production-запуска оставить одну чистую начальную миграцию.
7. Обновить OpenAPI, документацию, сценарии проверки и CI; проверить конкурентность, ошибки и настоящие Kafka/PostgreSQL.

## Соответствие проверке

- Горизонтальный внешний слой: stateless HTTP между запросами, кроме локальной оптимизации дедупликации; отдельный API Deployment/HPA, лимиты ресурсов/запросов.
- Cookie: случайный UUIDv4, подпись, HttpOnly/Secure/SameSite; отдельная route-cookie балансировщика.
- Повторы: bounded admission map и sticky routing; fallback на worker после потери памяти. Нет Redis/SQL на каждый синхронный vote.
- Очередь: Kafka acks=all до 202, partition key участника, configurable batching и deadlines.
- Worker: set-based SQL в своём темпе, уникальный ledger и атомарные агрегаты, offsets после успешной обработки всех шардов.
- Итоги: обезличенные агрегаты по вопросу/вариантам; новые индивидуальные варианты не сохраняются в SQL.
- Go: clean layers, интерфейсы, gofmt/vet/race, golangci-lint/gosec, govulncheck и CI.
- Тесты: unit/конкурентность, настоящая БД в CI, Kafka/PostgreSQL в Compose smoke/recovery; отдельный dockertest не обязателен при эквивалентном воспроизводимом окружении.
- Дополнительные пункты: Helm/Kubernetes, React voting/admin, OpenAPI 3.0.

## Существенные границы

Sticky routing не гарантирует неизменный под при сбое/масштабировании и может быть обойдён потерей route-cookie. Подлинная гарантия одного учтённого ответа — worker ledger. Куки не доказывают уникального человека. Память/пропускная способность рассчитываются для числа подов и retention; один под/Compose не заявляется способным принять весь пик. Настоящие испытания 1,8 млн RPS и cluster integration не требуются для тестового и здесь не заявлены выполненными.

## Работа с Git

Рабочие ветки именуются `feature/<branch_name>` и сливаются в `main`. Автор коммитов — `LimeOnTop` с GitHub noreply email; соавторские trailers не добавляются. Автоматические PR обновлений версий Dependabot отключены, чтобы не создавать ветки вне соглашения; проверка уязвимостей остаётся в CI.
